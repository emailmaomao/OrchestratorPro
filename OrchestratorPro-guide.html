The plain-language guide

OrchestratorPro

A robot workshop that builds parts of your app while you sleep — and hands you the parts to inspect before anything real changes.

01 / The whole thing in one breathWhat it actually is

OrchestratorPro is a machine that runs coding robots safely. Your project is whatever it points at.

Engine and car. The engine isn't the point on its own — it earns its keep by driving a real project. Point it at a different project tomorrow and the same engine works unchanged.

The kid version

Imagine you have a big LEGO castle on the dining table. It's the family castle — nobody's allowed to break it.

You have a helpful robot who's fast but sometimes wrong. So you don't let it near the table. Instead you give the robot its own photocopy of the castle in its own room, plus a note that says what to build.

When the robot says it's done, a tester machine shakes the castle to see if it falls over. If it falls over, that room gets thrown away and nothing happened. If it holds, the robot's work gets moved to a staging table next to the real one.

Then you walk over, look at the staging table, and decide whether it goes on the real castle. The robot is never allowed to touch the real castle. Not ever. That's the whole rule.

02 / The run, step by stepWhat happens after you press go

You hand it a short recipe file (a workflow YAML). It contains a goal, at most three steps, and which steps have to wait for which. Then it goes off alone and does this:

  1. 1

    Builds a private room for each step

    A git worktree — a separate working copy of the codebase, branched off the run's integration tip.

    Kid version: each robot gets its own photocopy — and importantly, robot #2's photocopy already includes whatever robot #1 finished. They can build on each other without bumping elbows.
  2. 2

    Sends a robot in

    An agent — Claude Code CLI under the hood, no API key needed — reads the step and writes code inside that room only.

    Kid version: the robot can only make a mess in its own room.
  3. 3

    Runs the gate

    Your project's own pytest suite is executed against the result. Not the agent's self-assessment — the actual tests.

    Kid version: the robot doesn't get to grade its own homework. A separate machine checks it. This is the single most important design choice in the whole system.
  4. 4

    Keeps only what passed

    Passing work is committed and merged onto orchestrator/<run>/integration. Failing work doesn't get in.

    Kid version: the staging table. Close to the real castle, but not the real castle.
  5. 5

    Writes down everything it did

    A full JSONL transcript plus an event log — every turn, every command, every result.

    Kid version: a flight recorder. If something looks weird later, you can read exactly what the robot was thinking.

And then it stops

The engine will not merge to main. That refusal is deliberate and hard-coded. You review the integration branch as a diff — same as reviewing any pull request from a coworker — and you decide whether it becomes part of your project's real history.

03 / Decoder ringThe words that made it confusing

  • worktreethe private room

    A second (or third) full checkout of your repo on disk, each on its own branch. Lets two agents work at once without stepping on each other's files.

  • integration tipthe newest staging state

    The most recent commit on the run's integration branch. New rooms branch off it, which is how step 2 can see step 1's finished work.

  • the gatethe shake test

    Just your project's own test suite, used as a pass/fail door. Code that doesn't pass never reaches the integration branch.

  • integration branchthe staging table

    orchestrator/<run>/integration — a throwaway branch holding the run's accumulated passing work, waiting for your review.

  • JSONL transcriptthe flight recorder

    A log file where each line is one JSON object — one event. Easy to replay, easy to grep, easy to load into pandas if you ever want to analyze runs.

  • workflow YAMLthe recipe card

    The small file you write by hand: goal, ≤3 steps, dependencies. Today this is the human part — you translate a roadmap line into it yourself.

  • notional_cost_usdan estimate, honestly labeled

    A rough token-cost figure from the CLI-backed model. Deliberately named so nobody mistakes it for a real invoice. Don't budget against it.

04 / ReceiptsThree real runs, and what each one taught

This isn't a demo. Three real tasks have gone through it on a live codebase, and the interesting part is the pattern in what the gate missed.

Run 1 — service extraction

Extracted a service out of a monolithic module

Robot did
Pulled the service out and fixed a real aliasing bug — to_dict() was handing back internal state by reference.
Gate said
Green.
You caught
A copy-tax regression in an @undoable decorator. Tests had no opinion about it.
Outcome
Fixed it yourself, adopted the branch.

Run 2 — typed attributes

Typed-attribute foundation

Robot did
Built the foundation. 3/3 steps green.
Gate said
All clear.
You caught
The migration function was never wired into src/ — a data-loss-shaped bug that no test could possibly see, because the untested code path simply never ran.
Lesson
A green gate proves the code works. It does not prove the code is connected.

Run 3 — faceted filtering

A filtering engine over document attributes

Robot did
Overrode a flawed instruction in the prompt — and was right to: an untagged document must stay fully functional.
Gate said
Green.
Lesson
The agent isn't only a typist. It occasionally has better product judgment than the prompt it was handed — which is a reason to read the diff, not a reason to skip reading it.

The common thread

The gate answers "does this code work?" It cannot answer "is this the right shape, wired in correctly, and what the product actually needs?" Every single run so far, your review has done real work. That's not a flaw to fix — it's the honest deal: supervise outcomes, not keystrokes. Not "supervise nothing."

05 / Driving itHow to actually use it on a new project

Clear this up first

It is not a prompt. You never tell an AI "please use OrchestratorPro."

OrchestratorPro is a program on your machine. It is the thing that uses the AI — not something you ask the AI to do. You run it from a terminal, and it launches Claude Code CLI as a subprocess, feeds it the step, and watches what comes back.

If you're typing into a chat window, you are not using OrchestratorPro. Your only two inputs are a YAML file and a command.

Command words versus placeholders

This trips everyone up once. Every invocation is the program, then a command word:

PS> .\.venv\Scripts\orchestratorpro.exe <command word> [options]

Command words — version, run, serve, config — are typed literally. They are never something you fill in. So orchestratorpro.exe version really is the word version, and it prints:

orchestratorpro 1.0.0

Anything in angle brackets, like <PATH TO YOUR PROJECT>, is a placeholder — replace it, brackets and all.

Anatomy of a command

Commands read left to right in three parts. This one confuses everybody the first time, because workflow and workflows are almost the same word doing completely different jobs:

.\.venv\Scripts\orchestratorpro.exe   workflow check   workflows\example.yaml
|                                     |                |
the program                           command           a real file path
                                      (group + action)  (folder\file on disk)

  • workflowsingular

    A command group, like config or backup.

  • checkthe action

    Together they mean "validate a recipe file".

  • workflows\example.yamlplural

    An actual path — the workflows folder inside your clone, and the file inside it. Relative to wherever you currently are, which is why every example has you cd into the clone first.

Same idea for the main one — run is the action, the rest is a real path:

orchestratorpro.exe   --repo D:\AiProjects\MyNewApp01   run   workflows\smoke.yaml
|                     |                       |     |
program               which project to        |     which recipe to follow
                      work on                 action
CommandWhat it doesWhen
versionPrints the version. Proves the install worked.Once, after installing
config checkValidates settings, reports anything unsafe.After editing config.toml
config showEvery setting actually in effect, as JSON.When something behaves oddly
workflow check <file>Validates a recipe without running it.Before every run

Where the options go

Before the command word (these are global):

OptionMeaning
--repo <path>The project to work on. Without it, run refuses.
--jsonMachine-readable output, for scripting
--log-level debugShow what it is actually doing
--database <path>Use a different run database
--config <path>Use a different settings file

After run:

OptionMeaning
--workspace <path>Where worktrees get created
--max-concurrency <n>How many steps may run at once
--allow-unverifiedRun with nothing gated or committed. Rarely what you want.
# correct
PS> orchestratorpro.exe --repo C:\proj run workflows\smoke.yaml

# WRONG - --repo after the command word
PS> orchestratorpro.exe run --repo C:\proj workflows\smoke.yaml

And when stuck, ask the tool: --help works on the program and on every command word.

What a new project needs before it can be driven

All five, or the engine is either useless or unsafe on it:

  1. A git repo with a clean tree. Worktrees and branches are the whole safety model. No git, no isolation.
  2. A real test suite. This is non-negotiable — the tests are the gate. A project with no tests gives the engine nothing to judge with, and you're back to trusting the agent's self-report.
  3. Tests that run from one command, fast enough to run every step. If the suite takes 20 minutes, a 3-step run costs an hour of gate time.
  4. Claude Code CLI installed and signed in. No API key — the engine shells out to the CLI you're already authenticated with.
  5. Disk space for worktrees. Each step is a full checkout, and nothing prunes them yet.

Step 1 — install it (one time)

This is exactly what someone arriving from GitHub types. They clone into whatever folder they like.

Windows — PowerShell

# make a folder to work in, and go into it
PS> mkdir <YOUR DRIVE LETTER>:\<Your Code FolderName>   # only if it doesn't exist yet
PS> cd    <YOUR DRIVE LETTER>:\<Your Code FolderName>   # change into your local folder

PS> git clone https://github.com/emailmaomao/OrchestratorPro.git
PS> cd OrchestratorPro
PS> .\scripts\install.ps1
PS> .\.venv\Scripts\orchestratorpro.exe version   # prints: orchestratorpro 1.0.0

Sample — real values filled in

PS> mkdir D:\AiProject
PS> cd    D:\AiProject
PS> git clone https://github.com/emailmaomao/OrchestratorPro.git
PS> cd OrchestratorPro
PS> .\scripts\install.ps1
PS> .\.venv\Scripts\orchestratorpro.exe version   # prints: orchestratorpro 1.0.0

macOS / Linux

$ mkdir -p ~/<Your Code FolderName>
$ cd ~/<Your Code FolderName>
$ git clone https://github.com/emailmaomao/OrchestratorPro.git
$ cd OrchestratorPro
$ ./scripts/install.sh
$ .venv/bin/orchestratorpro version

That last line printing a version is the proof it worked. The script creates a .venv inside the clone — it never touches the system Python.

Docker Compose and pip install -e . also work; the script is just the shortest path. Anyone wanting to work on OrchestratorPro rather than with it goes to docs/130_DEVELOPER_GUIDE.md.

They also need Claude Code on their PATH with a live session (skip if already signed in) — this is what makes the whole thing run without an API key:

$ claude auth

Step 2 — configure it once, forever

Put the settings in a file rather than in the shell — PowerShell $env: variables die when you close the window, which is the single most common reason a setup "stops working."

Create C:\Users\<you>\.orchestratorpro\config.toml on Windows, or ~/.orchestratorpro/config.toml on macOS and Linux:

[agent]
adapter = "claude_code"
model   = "sonnet"

[provider.claude_cli]
executable = "claude"

[gates]
test_command = "pytest -q"
parser       = "pytest"
timeout_s    = 900.0
PS> .\.venv\Scripts\orchestratorpro.exe config check
# "configuration is valid" = done. Never type $env: again.

Exit 0 is valid; 3 means it refused as unsafe and names the setting. This file is read automatically on every run, from any directory, in any new shell.

Step 3 — validate the workflow file

Free and instant. Catches an unknown dependency, a duplicate step name, or a cycle before you spend anything:

PS> .\.venv\Scripts\orchestratorpro.exe workflow check workflows\example.yaml

Step 4 — the real workflow schema

Copy workflows/example.yaml and edit it — this is the real schema:

name: extract-tag-service
goal: >
  One paragraph describing what the whole run is for.
max_concurrency: 1

defaults:
  max_attempts: 2
  gates: [tests]
  expects_changes: true

steps:
  - name: extract
    title: services/tag_filter.py - the logic, without the widget
    prompt: |
      The full instruction to the agent. Be specific about what
      to create, what to test, and what NOT to touch.

  - name: wire
    title: Route every caller through the new service
    depends_on: [extract]
    prompt: |
      Update every caller in src/ and verify no import of the
      old code path remains anywhere.

Note name, not id. And defaults.gates: [tests] is what points each step at the gate — which resolves to [gates] test_command in config, defaulting to pytest -q.

Always include a "wire it in" step. A run can pass every test while leaving the new code connected to nothing — tests only check the code they can reach.

Step 5 — run it

One command. --repo is a global option, so it goes before the word run — putting it after gives you unrecognized arguments: --repo.

Windows

PS> .\.venv\Scripts\orchestratorpro.exe --repo D:\AiProjects\MyNewApp01 run workflows\example.yaml

macOS / Linux

$ .venv/bin/orchestratorpro --repo ~/code/their-project run workflows/example.yaml
extract-tag-service: succeeded
  run     run_01J...
  steps   2/2 succeeded
  branch  orchestrator/run_01J.../integration
  review the diff before merging; nothing reached main

Exit codes are the contract: 0 every step succeeded, 1 something didn't, 2 bad invocation, 3 refused as unsafe. Without --repo it refuses outright rather than producing unverified work.

Step 6 — review and adopt

PS> cd D:\AiProjects\MyNewApp01
PS> git diff main...orchestrator/<run-id>/integration
PS> git merge --no-ff orchestrator/<run-id>/integration

The engine stops before this. Always.

Or use the server

Same pipeline, plus a dashboard, live progress, an approval queue, and a REST API:

PS> .\.venv\Scripts\orchestratorpro.exe --repo D:\AiProjects\MyNewApp01 serve
# dashboard: http://127.0.0.1:8765/ui/

One-time versus every-time

ThingHow often
install.ps1Once per computer
config.tomlOnce per computer
claude authOnce, until the session expires
Writing a workflow YAMLOnce per job
The run commandEvery time you want work done
Setting $env: variablesNever

Nothing runs in the background. Nothing starts at boot. run finishes and exits; serve lives only as long as its window stays open.

What changes for a brand-new project

Two things. Everything else is identical:

  1. The --repo path. It must be a git repo with a clean tree.
  2. [gates] test_command in config.toml, if that project doesn't run its tests with pytest -q.

How to tell whether a task belongs in the engine at all

Ask one question: if the agent got this wrong, would a test notice?

Yes → good candidate. Refactors, extractions, service boundaries, data transforms, parsers, anything with a clear right answer that pytest can assert.

No → do it yourself. Anything visual, anything about layout or feel, anything where "correct" is a judgment call. The engine will hand you a confident green run on a UI canvas that renders as garbage, and it will have no idea.

06 / Sharp edgesWhere it doesn't help yet

Knowing these keeps you from reaching for it wrong.

  • No visual verification. If your project has a GUI, a canvas-touching feature can pass every test and still look completely broken, and the engine will report nothing but green.
  • The LLM planner still isn't wired in. Goal → workflow, no human decomposition — it exists as code, but has never been run against a real task and isn't wired into the API or CLI. You are still the planner.
  • Partial cleanup only. orchestratorpro retention plan / apply / verify archives and prunes old runs from the database — but worktrees and transcripts are covered by nothing. Clean <workspace>/worktrees/ and <db-dir>/transcripts/ by hand.
  • Cost numbers are estimates. With the Claude CLI backend, cost_usd is null and notional_cost_usd carries a scale estimate charged to nobody. Attempts also flag tokens_estimated — one estimate makes the whole run's total an estimate.

07 / The bottom lineWhat to trust it with today

"Here's a well-scoped, logic-shaped, test-covered backlog item — hand me a reviewed integration branch." Yes. This works now.

"Here's the roadmap, go." Not yet. That needs the planner running, and visual verification for anything with a GUI.

Two human touchpoints per run: you write the recipe at the start, and you approve the diff at the end. Everything in between runs unattended. That gap is the whole product.
